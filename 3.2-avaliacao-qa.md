## Exercício 3.2 — Revisão crítica dos testes gerados por IA

**Tópico:** Revisão Crítica de Outputs de IA

### Armadilhas obrigatórias nos 3 testes

| Teste | Problema central | Se não identificou |
|-------|------------------|--------------------|
| **#1 — assertions vagas** | `toBeDefined()` testa existência, não correção. Passa mesmo se o endpoint retornar resposta errada ou sem fonte. | D4 ≤ 2 |
| **#2 — dados irreais** | Edge case de input vazio é válido, mas nenhum teste do conjunto exercita o domínio NovaTech (carga perigosa, SLA, frete, devolução). | D4 ≤ 2 |
| **#3 — mock que mascara bug** | Mock tão permissivo (`jest.fn().mockResolvedValue`) que o teste passa mesmo se a validação de input não existir ou retornar erro. | D4 ≤ 1 |

**Ponto de atenção contextual:** Os testes usam `jest` (`jest.fn`, `jest.mock`), mas o projeto usa **Vitest** (ver Anexo C e AGENTS.md). Identificar essa inconsistência demonstra atenção ao contexto do projeto, não apenas ao código isolado. Não bloqueia score 3 se o resto estiver forte, mas é esperado em um D4 = 3.

### Critérios

| Critério | Score 3 | Red flag (≤ 1) |
|----------|---------|-----------------|
| Análise própria ANTES do Claude | Identifica os 3 problemas principais de forma independente com justificativa | Análise vazia ou copiada do Claude |
| Inconsistência jest/Vitest | Identificada e apontada como problema contextual | Não notada (atenção: não bloqueia score 3 isoladamente) |
| Teste 1 reescrito corretamente | Verifica conteúdo da resposta (prazo correto, citação de fonte), usa dados de domínio, tem arrange/act/assert | Reescrita com assertion `toBeDefined()` ainda presente |
| Comparação com Claude honesta | Documenta o que cada um encontrou — incluindo o que o Claude pegou e o participante não pegou | "Concordamos em tudo" sem evidência |
| Classificação de risco | Cada problema classificado por impacto (teste passa mas código está errado?) | Apenas lista de problemas sem análise de risco |

### Checklist de verificação

- [ ] Teste #1: identificado como insuficiente por `toBeDefined()` sem verificar conteúdo?
- [ ] Teste #2: identificado como incompleto por ausência de dados de domínio NovaTech?
- [ ] Teste #3: identificado como perigoso por mock permissivo que mascara ausência de validação?
- [ ] Inconsistência jest/Vitest foi mencionada?
- [ ] O Teste 1 reescrito usa dados de domínio (ex: carga perigosa, SLA Gold)?
- [ ] O Teste 1 reescrito verifica campo `source_document` e conteúdo da `answer`?
- [ ] O Teste 1 reescrito usa `msw` ou mock adequado (não `jest.fn` diretamente)?
- [ ] A análise própria antecede o uso do Claude?
