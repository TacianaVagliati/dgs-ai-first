# Skill de Avaliação — Tech Lead (Cenário 3)

> **Programa:** Trilha de Certificação AI First — DGS / DB1 Global Software
> **Escopo:** Cenário-Âncora 3 — Fase de Governança e Validação (exercícios 3.1 e 3.2)
> **Referência:** Usar com `avaliacao-foundation.md` para dimensões e escala.

**Perfil:** Projeta o harness técnico completo (5 camadas) e faz revisão de risco dos artefatos gerados por IA antes do go-live. Demonstra visão arquitetural de como structured outputs, HITL e observabilidade se combinam num sistema de produção, e identifica riscos reais em artefatos parcialmente gerados por IA.

**Ferramentas esperadas:** Claude (chat) + GitHub Copilot em ambos os exercícios.

## Exercício 3.1 — Design do harness do projeto

**Tópico:** Harness Engineering

### Armadilhas obrigatórias

| Situação | Avaliação correta | Se não identificou |
|----------|-------------------|--------------------|
| **Harness cobrindo menos de 5 camadas** | Todas as 5 camadas devem estar presentes: Tool orchestration, Verification loops, Context & memory, Guardrails, Observability. Um harness com apenas Guardrails e Observability não demonstra domínio do framework completo. | D1 ≤ 2 |
| **Context & memory sem conexão à ADR-0002** | A camada de Context & memory DEVE referenciar o context budget definido na ADR-0002 (cenário 1): ~4K tokens para system prompt + ~8K para chunks + query + 3 turnos. Reinventar a estratégia de contexto sem consultar a ADR ignora decisões arquiteturais existentes. | D5 ≤ 2 |
| **Função de verificação que não bloqueia — só retorna booleano ou loga** | A função deve marcar a resposta como suspeita (campo no retorno ou exceção) de forma que o pipeline possa agir sobre isso. Retornar apenas `true/false` sem que o chamador saiba o que fazer não é uma verificação funcional. | D3 ≤ 2 |

### Critérios

| Critério | Score 3 | Red flag (≤ 1) |
|----------|---------|-----------------|
| 5 camadas cobertas com especificidade NovaTech | Cada camada tem conteúdo concreto do projeto (ex: Tool orchestration menciona o pipeline de ingestão → retrieval → LLM, não apenas "coordenação de ferramentas") | Camadas genéricas ou menos de 5 presentes |
| Context & memory conectado à ADR-0002 | Referencia explicitamente o context budget: 5 chunks × ~1.500 tokens, truncamento de histórico em 3 turnos, tamanho do system prompt | Sem menção à ADR-0002 ou reinventa a estratégia |
| Guardrails menciona structured outputs e HITL | Explica que structured outputs (Zod) são determinísticos e complementam o prompt (probabilístico). Inclui ao menos 1 ponto de HITL concreto | Guardrails apenas via prompt; sem HITL |
| Função de verificação funcional | Recebe a resposta do modelo, verifica `source_document` contra lista de IDs válidos (`POL-001`, `PROC-042`, `PROC-042-v2`, `SLA-2024`, `FAQ-Atendimento`), retorna resultado acionável | Função que apenas loga ou retorna booleano sem contexto |
| Gap analysis honesta | Para cada camada: o que já está implementado vs o que falta. Não apresenta tudo como resolvido | Tudo como "já implementado" sem evidência |

### Checklist de verificação

- [ ] Camada 1 (Tool orchestration): pipeline ingestão → retrieval → geração descrito?
- [ ] Camada 2 (Verification loops): verificação de fonte e schema mencionadas?
- [ ] Camada 3 (Context & memory): ADR-0002 referenciada com números concretos (tokens, turnos)?
- [ ] Camada 4 (Guardrails): structured outputs + HITL com ao menos 1 exemplo concreto?
- [ ] Camada 5 (Observability): logs, métricas e alertas mencionados?
- [ ] A função verifica `source_document` contra a lista exata de IDs válidos?
- [ ] A lista de IDs usa os identificadores curtos: `POL-001`, `PROC-042`, `PROC-042-v2`, `SLA-2024`, `FAQ-Atendimento`?
- [ ] A função retorna um resultado acionável (não apenas booleano solto)?
- [ ] A distinção entre verificações determinísticas (código) e probabilísticas (prompt) está articulada?

## Exercício 3.2 — Revisão crítica da arquitetura gerada com IA

**Tópico:** Revisão Crítica de Outputs de IA

### Armadilhas obrigatórias nos artefatos gerados com IA

| Artefato | Risco obrigatório a identificar | Se não identificou |
|----------|---------------------------------|--------------------|
| **2 skills sem refinamento** | Skills usadas sem refinamento após testes podem gerar outputs inconsistentes — o Copilot pode seguir padrões incorretos ou incompletos. O risco aumenta porque são as skills que o Copilot usa para gerar código de produção. | D4 ≤ 2 |
| **System prompt sem documentação de mudanças** | 6 iterações sem registro de por que cada mudança foi feita = sem possibilidade de rollback informado. Se o assistente regredir após uma mudança, não há como saber qual alteração causou o problema. | D4 ≤ 2 |
| **AGENTS.md com 15 páginas sem revisão recente** | AGENTS.md muito longo pode ter seções contraditórias entre si ou com as skills. Refinado 4 vezes mas sem teste de que o Copilot realmente segue as regras. | D4 ≤ 2 |

### Critérios

| Critério | Score 3 | Red flag (≤ 1) |
|----------|---------|-----------------|
| Análise própria ANTES do Claude | Identifica as 3 armadilhas principais de forma independente com classificação de severidade | Análise vazia ou posterior ao Claude |
| Skills sem refinamento como risco | Explicação de por que skills não testadas geram risco de regressão nos outputs do Copilot | Não menciona as skills |
| System prompt sem documentação como risco de governança | Articula que sem histórico de mudanças não há rollback informado — não é apenas "falta de boas práticas" | Menciona superficialmente sem impacto concreto |
| Priorização pragmática (2 semanas) | Foca no que reduz mais risco no tempo disponível. System prompt e skills (risco imediato de go-live) antes de AGENTS.md (risco operacional, não de go-live imediato) | Priorização sem critério ou tudo igual |
| Comparação com Claude honesta | Documenta o que cada um encontrou — incluindo o que o Claude pegou e o TL não pegou | "Concordamos em tudo" |
| Risco residual explícito | Define o que aceita como risco residual e por quê (ex: AGENTS.md longo pode ser revisto pós go-live) | Sem definição de risco residual |

### Checklist de verificação

- [ ] As 2 skills sem refinamento foram identificadas como risco?
- [ ] O impacto das skills não refinadas foi explicado (outputs inconsistentes do Copilot)?
- [ ] O system prompt sem documentação foi identificado como risco de governança?
- [ ] O rollback impossível (sem histórico de mudanças) foi articulado como consequência?
- [ ] O AGENTS.md com 15 páginas foi avaliado quanto a possíveis contradições internas?
- [ ] A análise própria antecede o uso do Claude?
- [ ] A priorização é explícita (o que verifica primeiro em 2 semanas)?
- [ ] O risco residual é definido (o que aceita sem verificar antes do go-live)?
- [ ] A comparação humano vs Claude documenta divergências reais?
