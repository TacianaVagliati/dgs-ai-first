## Contexto

Checklist de revisão para testes de integração gerados por IA no projeto NovaTech (Azure Function — query endpoint). Deve ser aplicado por QA em cada teste antes do merge. Estimativa: ~90 segundos por teste, divididos em 5 blocos temáticos.

**Regra de aprovação:** qualquer item marcado como ❌ devolve o teste para reescrita antes do merge.

---

## Bloco 1 — Nomenclatura (~20 segundos)

> Verifica se o teste é autoexplicativo apenas pelo nome, sem precisar ler o corpo.

- [ ] O `describe` usa o nome do módulo ou handler? (ex: `QueryHandler`, `FeedbackHandler`)
- [ ] O `it` começa com `'should'` e descreve **comportamento + condição**? (ex: `'should return explicit rejection when query involves dangerous goods return'`)
- [ ] Nenhum nome genérico presente? (ex: `'works'`, `'test'`, `'funciona'`, `'handler test'`)

---

## Bloco 2 — Estrutura (~20 segundos)

> Verifica se o padrão Arrange / Act / Assert está presente e completo.

- [ ] Os comentários `// Arrange`, `// Act` e `// Assert` estão presentes nos lugares corretos?
- [ ] O bloco `// Assert` contém ao menos uma assertion sobre **conteúdo concreto** (campo específico, valor esperado ou regex de domínio)?
- [ ] `toBeDefined()` **NÃO é** a única assertion do teste?

---

## Bloco 3 — Dados de Teste (~20 segundos)

> Verifica se os dados exercitam lógica real de domínio NovaTech — não dados genéricos.

- [ ] A pergunta no `// Arrange` pertence ao domínio NovaTech? (ex: carga perigosa, SLA Gold, multiplicador de frete, devolução, tier inexistente)
- [ ] Os chunks no mock são os corretos para o cenário? (ex: `chunks.pol001B` para carga perigosa; `chunks.sla2024A` para tier)
- [ ] Nenhum dado genérico presente? (ex: `"question": "test"`, `"question": "hello"`, `"question": "anything"`)

---

## Bloco 4 — Mocking (~20 segundos)

> Verifica se o servidor MSW está configurado corretamente e não há chamadas reais a serviços externos.

- [ ] `setupServer()` está presente com `beforeAll`, `afterEach` e `afterAll` configurados?
- [ ] `onUnhandledRequest: 'error'` está configurado no `setupServer()`?
- [ ] Nenhum `vi.spyOn` em módulo interno é usado como **principal mecanismo de validação**?
- [ ] Nenhuma variável de ambiente (`process.env.AZURE_*`) é acessada sem mock correspondente?

---

## Bloco 5 — Guardrails do Domínio (~10 segundos — aplicar apenas em testes de VC-03)

> Verifica se os guardrails críticos de negócio estão sendo validados de forma negativa (o que NÃO deve aparecer).

- [ ] Testes de carga perigosa + devolução verificam que `"7 dias úteis"` **NÃO aparece** na resposta? (`expect(body.answer).not.toMatch(/7 dias úteis/)`)
- [ ] Testes de tier inexistente verificam que SLAs inventados **NÃO aparecem**? (ex: `expect(body.answer).not.toMatch(/Platinum.*SLA/i)`)

---

## Resumo de Anti-Padrões Comuns (referência rápida)

| Anti-padrão                           | Como identificar                                           | Bloco de revisão |
| ------------------------------------- | ---------------------------------------------------------- | ---------------- |
| `toBeDefined()` como única assertion  | `expect(result).toBeDefined()` sem nada mais               | Bloco 2          |
| Dado genérico na pergunta             | `"question": "test"` ou `"question": "hello"`              | Bloco 3          |
| Spy em método interno                 | `vi.spyOn(searchService, 'query')` como assertion principal | Bloco 4         |
| Mock permissivo sem validação         | `mockResolvedValue({ results: [] })` para qualquer query   | Bloco 4          |
| `onUnhandledRequest` ausente          | `setupServer()` sem a opção de erro                        | Bloco 4          |
| Nome genérico no `it`                 | `'works'`, `'funciona'`, `'test'`                          | Bloco 1          |
| Guardrail sem assertion negativa      | Teste de VC-03 sem `.not.toMatch()`                        | Bloco 5          |
