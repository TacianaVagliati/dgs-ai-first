## Exercício 3.1 — Structured output e verificações determinísticas

**Tópico:** Harness Engineering

### Armadilhas obrigatórias

| Situação | Avaliação correta | Se não identificou |
|----------|-------------------|--------------------|
| **Guardrails que apenas logam em vez de bloquear** | Os 2 guardrails DEVEM bloquear a resposta inválida e retornar resposta padrão segura. Apenas registrar o problema em log e deixar a resposta passar é insuficiente — é a armadilha mais comum de código gerado por Copilot para guardrails. | D3 ≤ 2 (regra de corte da Foundation) |
| **Schema Zod aceitando campos extras sem `.strict()`** | Um schema sem `.strict()` aceita qualquer campo adicional silenciosamente, o que pode mascarar mudanças de contrato. O code review deve identificar isso. | D4 ≤ 2 |
| **Regex de carga perigosa cobrindo apenas "carga perigosa" literalmente** | A variação do tema (gases, explosivos, inflamável, ANTT, classe 3) deve ser coberta pelo guardrail. Regex que só detecta a string exata "carga perigosa" deixa passar variações. | D4 ≤ 2 |

### Critérios

| Critério | Score 3 | Red flag (≤ 1) |
|----------|---------|-----------------|
| Schema Zod válido e correto | `answer` (string), `source_document` (string ou null), `confidence_score` (number 0-1). Tipagem correta, campos obrigatórios definidos | Schema com tipos errados ou campos faltando |
| Guardrail 1 bloqueia (não só loga) | Se `source_document` ausente/nulo: retorna resposta padrão segura. Não deixa passar com log. | Apenas `logger.warn(...)` sem rejeição |
| Guardrail 2 bloqueia (não só loga) | Se carga perigosa + devolução afirmativa detectados: retorna resposta de redirecionamento ao ramal 4500. Não deixa passar com log. | Apenas `logger.warn(...)` sem rejeição |
| Code review identifica ≥ 2 problemas reais | Problemas concretos do código gerado (não inventados): schema sem `.strict()`, regex limitada, falta de tipo de retorno, etc. | Problemas genéricos ou inventados |
| Distinção prompt vs código clara | O participante explica por que a verificação determinística no código é mais confiável que instrução no prompt para guardrails de alto risco | Confunde os dois mecanismos |

### Checklist de verificação

- [ ] Schema Zod tem os 3 campos obrigatórios: `answer`, `source_document`, `confidence_score`?
- [ ] Tipagem correta: `answer: z.string()`, `source_document: z.string().nullable()`, `confidence_score: z.number().min(0).max(1)`?
- [ ] Guardrail 1 (fonte ausente) rejeita a resposta e retorna fallback — não apenas loga?
- [ ] Guardrail 2 (carga perigosa + devolução) bloqueia respostas afirmativas — não apenas loga?
- [ ] O code review menciona `.strict()` (ou equivalente) para rejeitar campos extras?
- [ ] O code review menciona cobertura de variações no regex de carga perigosa?
- [ ] O código final está em `/src/services/response-validator.ts` (conforme Anexo C)?
- [ ] A distinção prompt (probabilístico) vs código (determinístico) está articulada?

## Exercício 3.2 — Revisão crítica de código gerado por IA

**Tópico:** Revisão Crítica de Outputs de IA

### Armadilhas obrigatórias no código gerado pelo Copilot

| Problema | Classificação | Se não identificou |
|----------|--------------|---------------------|
| **`as any` sem validação Zod** | Violação do AGENTS.md (TypeScript strict mode exige tipagem; `as any` bypassa toda verificação de tipo) | D4 ≤ 2 |
| **`console.log` em vez de pino** | Violação do AGENTS.md ("pino para logging — nunca console.log") | D4 ≤ 2 |
| **`require` dinâmico no corpo da função** | Violação do AGENTS.md ("imports estáticos no topo — nunca require dinâmico"). Também é problema de performance. | D4 ≤ 2 |
| **`attendantEmail` sendo logado** | Violação de segurança + AGENTS.md ("nunca logar dados pessoais — e-mail, nome"). LGPD/GDPR. | D4 ≤ 1 |

**Nota:** Um participante que não identifica o log de `attendantEmail` demonstra falta de atenção a dados pessoais — o problema mais sério do código.

### Critérios

| Critério | Score 3 | Red flag (≤ 1) |
|----------|---------|-----------------|
| Análise própria ANTES do Claude | Identifica os 4 problemas principais de forma independente com classificação correta | Análise vazia ou posterior ao Claude |
| Classificação dos problemas | Cada problema classificado: violação AGENTS.md / segurança / bug potencial | Lista sem classificação |
| Código reescrito correto | Resolve todos os problemas: Zod para validação, pino para log, import estático, sem dado pessoal no log | Código reescrito ainda com algum dos problemas |
| Comparação com Claude honesta | Documenta o que cada um encontrou — sem "concordamos em tudo" se houve divergência | Comparação ausente |
| Conformidade com AGENTS.md | O código final segue: TypeScript strict, Zod, pino, imports estáticos, sem dados pessoais em log | Código final ainda viola alguma regra |

### Checklist de verificação

- [ ] `as any` identificado e corrigido com schema Zod para validar o body?
- [ ] `console.log` identificado e substituído por `pino` no código reescrito?
- [ ] `require` dinâmico identificado e convertido para import estático no topo?
- [ ] Log de `attendantEmail` identificado como violação de dados pessoais?
- [ ] O código reescrito não loga nenhum dado pessoal (email, nome do atendente)?
- [ ] A análise própria antecede o uso do Claude?
- [ ] O código final está tipado corretamente (sem `as any`)?
- [ ] O código final segue a estrutura esperada em `/src/functions/feedback/handler.ts`?
