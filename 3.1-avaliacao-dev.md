> **Programa:** Trilha de Certificação AI First — DGS / DB1 Global Software  
> **Escopo:** Cenário-Âncora 3 — Fase de Governança e Validação (exercícios 3.1 e 3.2)  
> **Referência:** Usar com `avaliacao-foundation.md` para escala, regras de corte e classificação final.

**Perfil:** Implementa o harness de código que torna o assistente confiável: structured output validável + guardrails determinísticos que bloqueiam (não apenas logam) respostas inválidas. Demonstra que sabe revisar código gerado por IA contra o AGENTS.md e identificar riscos além do que o Copilot verifica.

**Ferramentas esperadas:** GitHub Copilot no 3.1 e 3.2 (geração + revisão); Claude (chat) como co-reviewer em ambos.

## Exercício 3.1 — Structured output e verificações determinísticas

**Tópico:** Harness Engineering

---

### Dimensões D1–D5 aplicadas a este exercício

| Dimensão | O que observar aqui |
|----------|----------------------|
| **D1 — Domínio Conceitual** | Articula a distinção entre prompt (probabilístico — o modelo pode "esquecer") e código (determinístico — a regra sempre executa). Explica por que structured output reduz os 12% de erros mencionados no cenário: campos obrigatórios validados programaticamente não dependem da atenção do modelo. |
| **D2 — Uso de Ferramentas** | Usa o Copilot para gerar o schema e o validator, mas faz code review ativo — não aceita o primeiro output. Usa o Claude para identificar problemas que o Copilot não sinaliza (ex: `.strict()` ausente, regex insuficiente). |
| **D3 — Qualidade do Entregável** | Schema Zod válido e restritivo. Código do `response-validator.ts` compila e aplica os 2 guardrails com bloqueio real (não só log). Code review com ao menos 2 problemas concretos e correções aplicadas. |
| **D4 — Pensamento Crítico** | Identifica as armadilhas no código gerado pelo Copilot (schema permissivo, guardrail que só loga, regex com cobertura insuficiente). Code review não é genérico — aponta linhas e propõe correção específica. |
| **D5 — Aplicabilidade ao Projeto** | O schema reflete os campos definidos no contexto do projeto (`answer`, `source_document`, `confidence_score`). Os guardrails implementados são os 2 do enunciado — não reinventa novos. Referencia o repositório (`/src/services/response-validator.ts`) e o AGENTS.md. |

---

### Armadilhas obrigatórias (verificar no code review)

| Problema | Avaliação correta | Se não identificou |
|----------|-------------------|--------------------|
| **Guardrail que só loga, não bloqueia** | **Crítico.** Se a verificação de `source_document` ou a detecção de carga perigosa + devolução registra o problema mas retorna a resposta original, o guardrail não funciona. O código deve substituir a resposta por mensagem padrão segura. | D3 ≤ 2 (regra de corte da Foundation) |
| **Schema Zod que aceita campos extras** | **Problema de harness.** Se o schema usa `.object({...})` sem `.strict()`, campos inesperados passam silenciosamente. O Copilot frequentemente omite `.strict()`. | D4 ≤ 2 |
| **Regex de carga perigosa sem cobertura de variações** | **Bug latente.** Um regex como `/carga perigosa/i` não cobre "cargas perigosas", "carga classe 3", "líquido inflamável", "gases". O code review deve propor regex mais abrangente ou lista de termos. | D4 ≤ 2 |

**Calibração:** o cenário pede **2** guardrails, não todos os guardrails do projeto. Não penalizar por ausência de guardrails além do escopo. O que importa é que os 2 implementados realmente bloqueiam.

---

### Critérios de sucesso

| Critério | Score 3 | Red flag (≤ 1) |
|----------|---------|-----------------|
| Schema Zod válido e restritivo | Define os 3 campos com tipos corretos, usa `.strict()` para rejeitar campos extras, e tipos são apropriados (ex: `confidence_score` como `z.number().min(0).max(1)`) | Schema aceita `as any` ou não valida tipos — passa qualquer coisa |
| Guardrails bloqueiam ativamente | Ambas as verificações retornam resposta padrão segura quando acionadas — não apenas `console.log` ou `return true/false` sem ação | Qualquer guardrail que detecta o problema mas não substitui a resposta |
| Code review identifica problemas reais | Encontra ao menos 2 problemas concretos e específicos ao código (ex: `.strict()` ausente, regex insuficiente) — não problemas genéricos como "poderia ter mais testes" | Code review genérico ou que só elogia o Copilot |
| Distinção prompt vs código clara | Articula por que prompt é probabilístico e código é determinístico, conectando ao problema dos 12% de respostas incorretas do cenário | Trata guardrail de prompt e guardrail de código como equivalentes |

---

### Checklist de verificação contextual

> Usar durante a avaliação humana ou ao montar o prompt para avaliação por LLM.

- [ ] O schema Zod usa `.strict()`? (Se não, campos extras passam silenciosamente — armadilha mais comum do Copilot.)
- [ ] O guardrail de `source_document` ausente retorna resposta padrão — não só loga? (Verificar o `return` após detecção do problema.)
- [ ] O guardrail de carga perigosa + devolução bloqueia mesmo com reformulações da pergunta? (O regex cobre variações: "cargas perigosas", "líquido inflamável", "gases", "classe 3"?)
- [ ] O code review menciona linha ou trecho específico do código — ou é comentário genérico?
- [ ] O arquivo está em `/src/services/response-validator.ts` conforme o Anexo C?
- [ ] A distinção probabilístico vs determinístico está articulada no entregável — ou foi ignorada?
- [ ] Os tipos do schema correspondem aos campos do projeto (`answer: z.string()`, `source_document: z.string().nullable()`, `confidence_score: z.number().min(0).max(1)`)?

## Exercício 3.2 — Revisão crítica de código gerado por IA

**Tópico:** Revisão Crítica de Outputs de IA

---

### Dimensões D1–D5 aplicadas a este exercício

| Dimensão | O que observar aqui |
|----------|----------------------|
| **D1 — Domínio Conceitual** | Sabe por que cada violação do AGENTS.md importa — não é lista de "regras quebradas" sem contexto. Ex: entende que `console.log` não é capturado pelo pipeline de observabilidade; que `attendantEmail` no log é problema de privacidade, não só de convenção. |
| **D2 — Uso de Ferramentas** | Faz revisão própria ANTES do Claude. Usa o Copilot para reescrever o código — não reescreve manualmente o que o Copilot deveria gerar. Compara as revisões de forma crítica. |
| **D3 — Qualidade do Entregável** | O código reescrito compila (ou é plausível), usa Zod para input, pino para logging, import estático, e não loga `attendantEmail`. Todos os 4 problemas foram corrigidos. |
| **D4 — Pensamento Crítico** | Identifica os 4 problemas de forma independente, hierarquiza por gravidade (`attendantEmail` é o mais grave — privacidade), e articula o risco de cada um, não só a violação. |
| **D5 — Aplicabilidade ao Projeto** | Referencia o AGENTS.md do projeto (construído no cenário 2) como fonte de verdade. O código reescrito reflete o repositório (`/src/functions/feedback/handler.ts`). |

---

### Armadilhas obrigatórias no `feedback-handler.ts`

| Violação | Avaliação correta | Se não identificou |
|----------|-------------------|--------------------|
| **`as any` sem validação Zod** | **Violação do AGENTS.md + risco de segurança.** `body as any` bypassa todo o type system. Qualquer payload malformado entra sem rejeição. O AGENTS.md exige Zod para validação de input. | D4 ≤ 2 |
| **`console.log` em vez de pino** | **Violação do AGENTS.md.** O projeto usa pino para logging estruturado. `console.log` não é capturado pelo pipeline de observabilidade. | D4 ≤ 2 |
| **`attendantEmail` logado** | **Problema de privacidade + violação do AGENTS.md.** O AGENTS.md proíbe logar dados pessoais. `attendantEmail` está sendo serializado no JSON do log. | D4 ≤ 1 se não identificado — é o problema mais grave |
| **`require` dinâmico** | **Violação do AGENTS.md.** `const { CosmosClient } = require(...)` dentro da função viola a regra de imports estáticos no topo. Impede análise de dependências e tree-shaking. | D4 ≤ 2 |

**Ponto de atenção:** Os testes usam `jest` (`jest.fn()`) mas o projeto usa Vitest. Identificar essa inconsistência demonstra atenção ao contexto além do código isolado. Não bloqueia score 3 se o resto estiver forte — é diferenciador positivo.

---

### Critérios de sucesso

| Critério | Score 3 | Red flag (≤ 1) |
|----------|---------|-----------------|
| Análise própria ANTES do Claude | Lista os 4 problemas (ou ao menos 3) de forma independente, cada um classificado (violação AGENTS.md / segurança / bug potencial) | Análise própria vazia, superficial, ou feita após ver o output do Claude |
| Gravidade dos problemas hierarquizada | Identifica `attendantEmail` no log como o problema mais grave (privacidade + AGENTS.md) e articula por quê vai além de uma convenção de código | Todos os problemas tratados com o mesmo peso |
| Código reescrito segue o AGENTS.md | Usa Zod para validar input, pino para logging, import estático do CosmosClient no topo, e não loga `attendantEmail` | Código reescrito corrige alguns problemas mas mantém `console.log` ou `as any` |
| Comparação humano vs Claude honesta | Reconhece o que cada um encontrou, incluindo o que o Claude viu e o participante não viu — e vice-versa | "Encontramos os mesmos problemas" sem verificar ou "o Claude foi mais completo" sem análise |

---

### Checklist de verificação contextual

- [ ] A revisão própria está datada ou marcada como anterior ao uso do Claude?
- [ ] Os 4 problemas estão listados: `as any`, `console.log`, `require` dinâmico, `attendantEmail` no log?
- [ ] O `attendantEmail` foi identificado como problema de privacidade (não só "violação de convenção")?
- [ ] O código reescrito tem `import { CosmosClient } from '@azure/cosmos'` no topo (não dentro da função)?
- [ ] O código reescrito usa `pino` ou `logger.info(...)` — sem nenhum `console.log`?
- [ ] O input está validado com Zod antes de qualquer acesso aos campos (`queryId`, `rating`, etc.)?
- [ ] O objeto logado exclui `attendantEmail` (ex: loga `queryId` e `rating`, não o objeto `feedback` completo)?
- [ ] O participante mencionou a inconsistência `jest` vs Vitest? (Diferenciador — não obrigatório para score 3.)
